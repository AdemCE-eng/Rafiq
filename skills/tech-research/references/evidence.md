# Evidence decisions

Use this when a claim could change the learner's plan.

| Situation | Action |
| --- | --- |
| A model answer conflicts with official docs | Check version, date, implementation and context. Correct the model answer when the docs apply; explicitly retain any unresolved conflict. |
| Official specification and implementation differ | Explain the guarantee versus observed support. Do not declare either universally correct. |
| Two pages disagree | Compare versions and scope, cite both, and identify the small check that would resolve the difference. |
| Performance claim | Require workload, hardware, measurement method and baseline. Without these, call it a hypothesis and propose a benchmark. |
| Only community evidence is available | Label it as such; use it for discovery or a reproducible hypothesis, not a universal guarantee. |
| No browsing or blocked source | Say what was not verified. Ask for the relevant excerpt when it matters; give only provisional guidance otherwise. |
| Source cap prevents cross-checking | Spend the budget on the highest-impact claims; list remaining uncertainty. Never invent corroboration. |

For each important claim capture enough to audit it: claim, direct source,
version/date when relevant, and whether it is documented, observed, or inferred.
A short paragraph can do this; do not require a large evidence table.

For adoption decisions, compare the current approach with the technology against
the actual workload, target environment, maintenance cost and constraints. A
new technology is not automatically a useful one.

Stop when the decision is supported, or when further reading cannot resolve a
specific uncertainty and an experiment is more useful. Keep a few high-value
sources rather than padding a bibliography.
