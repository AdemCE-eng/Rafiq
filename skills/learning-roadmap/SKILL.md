# Learning roadmap

Produce a path, not a course by default. Reuse known context; ask only for missing
facts that materially change scope. Identify an observable finish line, current
ability, available time, and constraints. A job title is not proof of every
prerequisite; use one lightweight task only if that uncertainty affects the path.

Honor conversational preferences and any explicitly supplied preferences file.
Do not search for configuration. Missing preferences need no setup.

## Choose the learning shape

Read [path decisions](references/path-decisions.md) when the goal is broad,
foundations are missing, time is unrealistic, or fundamentals-first is preferred.

- Narrow build + relevant experience: small milestones tied to the build.
- Narrow feature + demonstrated prerequisites: begin at that feature.
- Broad competence, repeated conceptual gaps, or cumulative foundations:
  recommend a suitable course, book, curriculum, or sustained foundational path.
- Fundamentals-first: explain the necessary model before practice; do not force
  a project-first sequence. Keep practice as evidence of understanding.

Do not infer UNKNOWN prerequisites are either mastered or all required.
Classify each candidate topic by its contribution to the finish line:

- **NOW:** blocks the next milestone or prevents a material error in this goal.
- **LATER / NOT NEEDED YET:** useful if a named future requirement appears.
- **NOT NEEDED FOR THIS GOAL:** exclude with a short reason, without implying it
  is universally useless.

Do not reteach demonstrated knowledge. Treat reported knowledge as a starting
assumption, revising only on evidence. Use existing research; if a technical
uncertainty affects the plan, verify that narrow point with available sources or
mark the plan provisional. No other skill is required.

## Deliver and revise

Default to at most five initial topics, fewer when sufficient; preferences can
change this. Never hide a prerequisite just to meet a cap. If the necessary scope
exceeds time or topic limits, offer a reduced outcome or a longer path with the
tradeoff stated.

For each small milestone give an outcome, an approximate time range, one learner
action, and a checkable success condition. Reserve time for attempts, debugging,
and review, not just reading. Do not promise mastery in a single session.

Create an application/build target early when practical; for orientation, a
reasoned go/no-go decision is a valid target. Give the next action, not a full
implementation. On new gaps, change only the blocked part of the roadmap.
